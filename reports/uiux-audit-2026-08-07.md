### 총평

이 사이트는 접근성과 신뢰성 측면에서 이미 상위 수준이다. 42회 수집에서 **텍스트 대비비 위반 0건, 라벨 없는 폼 필드 0건, 접근 가능한 이름 없는 인터랙티브 요소 0건, 가로 스크롤 0건, alt 누락 0건, 중복 id 0건, 콘솔 에러 0건**이 나왔다. `0원 입력 확인` 모달은 형제 요소 32개에 `aria-hidden`을 걸고 Escape로 닫히며 포커스를 트리거 버튼으로 되돌린다 — 직접 확인했다. 금액 입력 시 `2,500만원` 환산값을 실시간으로 보여주는 처리, 판정 결론에서 색을 의도적으로 배제한 결정(ADR-001), 상단 상시 신원 고지는 모두 이 도메인(건강보험 준공공 정보)에서 정확히 옳은 선택이다. **다크패턴은 발견되지 않았고, P0(즉시 조치) 이슈도 없다.**

점수를 깎는 지점은 성격이 다르다. 결함이 아니라 **모바일 우선순위**의 문제다. 스티키 헤더는 390px에서 뷰포트의 16%, 320px에서 24%를 상시 점유하는데 그 안에 주 CTA가 없다(데스크톱 헤더에만 있다). 홈에서 핵심 태스크인 판정 폼은 문서 높이의 69% 지점에서 시작한다. 포커스 표시는 존재하지만 명도가 아니라 색상만 바뀌어 판별 대비가 1.27:1이다. 이 셋은 모두 **한 파일 한 곳 수정**으로 해결된다.

### 가장 먼저 고칠 3가지

1. **모바일 헤더에 `내 자격 확인` CTA 추가** — `src/app/layout.tsx` 모바일 nav 블록 1곳. 화면의 16~24%를 쓰면서 주 행동을 제공하지 않는 상태를 해소한다.
2. **`html { scroll-padding-top }` 전역 지정** — `src/app/globals.css` 24행 `html` 규칙에 3줄. `본문 바로가기` 스킵 링크가 헤더 뒤로 들어가는 문제와 앵커 이동 전반이 한 번에 해결된다.
3. **포커스 헤일로 색 교체** — `src/components/ui.tsx` 49행. `ring-accent-100`(#dff5f3, 흰 배경 대비 1.14:1)을 명도 대비가 있는 색으로.

## 4. P1 — 이번 스프린트

### [P1][반응형][측정] 모바일(<640px) 헤더에 주 CTA가 없다

**문제**
`src/app/layout.tsx`의 데스크톱 nav(`sm:flex`)에는 `내 자격 확인` 버튼이 있으나, 모바일 nav(`sm:hidden`, 133행)에는 텍스트 링크 4개만 있고 CTA 버튼이 빠져 있다.

**영향**
그럼에도 스티키 헤더는 상시 점유한다 — 390px에서 **134px(뷰포트의 16%)**, 320px에서 **182px(24%)**. 화면 면적을 계속 쓰면서 주 행동은 제공하지 않는다. 640px 이상에서만 CTA가 나타나므로 사실상 모든 휴대폰에서 영향을 받는다. 태스크 A 경로 2의 이탈 위험과 직접 연결된다.

**증거**
`layout.tsx` 120행(데스크톱 nav — 5번째 항목이 CTA) vs 133행(모바일 nav — CTA 없음). 헤더 높이는 iframe 뷰포트 시뮬레이션으로 320·390px에서 각각 측정.

**수정**
모바일 nav 마지막에 데스크톱과 동일한 CTA 링크를 추가한다. 헤더 높이를 더 늘리고 싶지 않다면 링크 4개를 2개(`가이드`·`검증 원칙`)로 줄이고 CTA를 넣어 총 높이를 유지한다.

**검증**
390·360·320px에서 헤더 높이 재측정(목표: 뷰포트의 20% 미만). GA에서 모바일 세션의 `judge_start` 발생률 개선 여부 확인.

### [P1][접근성][측정] `본문 바로가기`(#main) 이동 지점이 스티키 헤더에 가린다

**문제**
`html`에 `scroll-padding-top`이 없고(`auto`), `#main`과 `#evidence-checklist-title`의 `scroll-margin-top`이 `0px`이다. 앵커 이동 후 대상이 `top:0`에 놓여 헤더(데스크톱 69px / 모바일 134px) 아래로 들어간다.

**영향**
`본문 바로가기`는 키보드·스크린리더 사용자의 첫 진입점이다. 이 링크를 눌러도 본문 상단 69~134px가 헤더에 덮인 채로 화면이 멈춘다. 홈의 `#guides`·`#journey`는 `scroll-mt-96px`가 걸려 있어 정상 동작한다 — 같은 패턴이 화면마다 다르게 적용된 상태다.

**증거**
`location.hash` 이동 후 `getBoundingClientRect().top` 측정 — `#main` top=0 / 헤더 bottom=69, `#guides` top=96 / 헤더 bottom=69, `#evidence-checklist-title` top=0.

**수정**
`src/app/globals.css`의 `html` 규칙에 다음을 추가하면 개별 `scroll-mt` 없이 전역 해결된다.

```css
html {
  scroll-behavior: smooth;
  scroll-padding-top: 9rem;              /* 모바일 헤더 134px + 여유 */
}
@media (min-width: 640px) {
  html { scroll-padding-top: 6rem; }     /* 데스크톱 헤더 69px + 여유 */
}
```

**검증**
`본문 바로가기` 활성화 후 `main`의 `getBoundingClientRect().top ≥ 헤더 높이` 확인. 3뷰포트 전부. 기존 `scroll-mt-28`·`scroll-mt-96px`와 이중 적용되지 않는지 함께 확인.

### [P1][접근성][측정] 포커스 표시의 판별 대비가 1.27:1

**문제**
`select`·`input` 포커스 시 4px 헤일로 `#dff5f3`(accent-100)은 흰 배경 대비 **1.14:1**, 테두리는 `#64748b`(slate-500) → `#056d78`(accent-700)로 바뀌는데 두 색의 상호 대비가 **1.27:1**이다. 명도는 거의 그대로이고 색상(hue)만 바뀐다.

**영향**
WCAG 2.2 SC 2.4.7(포커스 가시성, AA)은 "변화가 있을 것"을 요구하므로 형식상 충족한다. 그러나 적록색약 사용자에게는 slate와 teal이 거의 같은 밝기로 보여 포커스 위치를 잃는다. 2.4.13 Focus Appearance(AAA)의 3:1 기준에는 미달. 11필드 폼을 키보드로 완주해야 하는 도구에서 영향이 크다.

**증거**
`getComputedStyle` 실측 — `boxShadow: rgb(223,245,243) 0 0 0 4px`, 포커스 테두리 `rgb(5,109,120)`, 비포커스 테두리 `rgb(100,116,139)`. 대비비는 WCAG 상대휘도 공식으로 계산.
`src/components/ui.tsx` 49행: `focus:border-accent-700 focus:outline-none focus-visible:ring-4 focus-visible:ring-accent-100`

**수정**
밝은 배경용과 어두운 배경용 포커스 토큰을 분리한다. 밝은 배경(폼 필드)에서는 명도 대비가 있는 색으로:

```
/* 밝은 배경 */ focus-visible:ring-2 focus-visible:ring-brand-900 focus-visible:ring-offset-2
/* 어두운 배경(SubmitButton, brand-900) */ 현재 ring-accent-100 유지 — 이 조합은 이미 고대비
```

`#17324d`(brand-900)는 흰 배경 대비 11:1이다. 어두운 버튼 위에서는 지금의 `accent-100` 헤일로가 오히려 정답이므로 일괄 교체하지 말 것.

**검증**
회색조 변환 스크린샷에서 포커스/비포커스 상태가 구분되는지 확인. 마우스 없이 판정 폼 완주 테스트.

### [P1][사용성][측정] 홈에서 핵심 태스크 진입까지 6,542px

**문제**
모바일 390px 기준 홈 문서 높이 9,536px 중 첫 입력 필드가 y=**6,542px**(전체의 69%). 760px 뷰포트로 **8.6화면 분량**을 스크롤해야 판정 폼에 닿는다. 그 앞에 시나리오·도구목록·가이드·FAQ 섹션 4개가 놓여 있다.

**영향**
히어로 CTA를 클릭한 사용자는 앵커 점프로 바로 도달하므로 문제없다. 스크롤로 탐색하는 사용자가 영향을 받는데, 이들은 되돌아갈 헤더 CTA도 없다(위 P1 항목).

**증거**
섹션 오프셋 실측 — 시나리오 y=1,324 / 도구목록 y=2,474 / 가이드 y=3,665 / CTA 섹션 y=5,856 / 판정 폼 y=6,542. 문서 높이 9,536px.

**수정**
재설계가 아니라 순서 조정으로 해결한다. 판정 폼을 시나리오 섹션 자리(y≈1,300)로 올리고 마케팅 섹션을 아래로 내린다. 또는 홈에는 `가입자와의 관계` 1문항만 노출하고 나머지는 `/health-insurance/dependent/`로 넘기는 축약 진입을 둔다.

**검증** `가설` 성격이 섞여 있으므로 데이터로 확인한다. GA에서 홈 스크롤 깊이 분포와 `judge_start` 이벤트의 발생 위치를 대조. A/B로 폼 위치 상단/하단 비교.

### [P1][접근성][측정] 목록 링크 터치 타깃이 19px

**문제**
36개 화면에서 24×24px 미만 타깃 294개가 검출됐다. 표본 검증 결과 **전부 `<li>` 직계 자식 링크**로, 높이가 일률적으로 19px다(14px 텍스트의 line-height).

**영향**
WCAG 2.2 SC 2.5.8 Target Size (Minimum)은 24×24 CSS px를 요구한다. 이 조항에는 "문장이나 텍스트 블록 안의 인라인 타깃" 예외가 있으나, 검사한 11개 전부 목록 항목이라 **예외가 적용되지 않는다.** 대상은 가이드 목차, `함께 읽기` 관련글, 외부 근거 링크, 브레드크럼(`홈` = 14×19px)이다. 브레드크럼 `홈`은 가로 14px로 Fitts 법칙상 특히 놓치기 쉽다.

**증거**
`/health-insurance/guides/pension-impact/` @390 — 목차 5개, 관련글 3개, 외부 링크 2개, 브레드크럼 1개 모두 h=19px. 화면당 검출 수: 가이드 12~15개, 검증 원칙 15개, 도구 4~6개.

**수정**
링크 자체 크기는 그대로 두고 히트 영역만 넓힌다. 목록 링크에 `inline-flex min-h-[24px] items-center` 또는 `py-1` 추가. 모바일에서 44px를 노리려면 `py-2.5`.

**검증**
재수집 후 `under24Count = 0` 확인. 시각적 줄간격이 무너지지 않았는지 가이드 목차 스크린샷 비교.

## 5. P2 — 백로그

### [P2][사용성][관찰] 긴 가이드에 상시 목차가 없다

**문제** 가이드 6편의 문서 높이가 데스크톱 5,064~6,429px, 모바일 7,262~9,439px인데 `이 글의 순서` 목차는 본문 흐름 안 최상단에만 있고 sticky가 아니다. 가이드 화면의 고정 요소는 헤더 하나뿐(`fixedViewportPct` 8%).
**영향** 스크롤 후 현재 위치를 알 수 없고(Nielsen #6 회상보다 인식), 다른 절로 이동할 수단이 없다.
**증거** 본문 컬럼은 768px 고정(`max-w-3xl`)이고 `main`은 1,521px(1536 창 실측) — 컨테이너 폭의 **약 49%가 빈 여백**이다(1440 창 기준 약 45%). 홈에는 이미 sticky aside(높이 575px)가 있으나 가이드에는 없다.
**수정** 홈의 sticky aside 패턴을 가이드에 재사용해 목차를 오른쪽 여백으로 옮긴다. 새 컴포넌트가 필요 없다. 모바일은 접힌 `<details>` 목차.
**검증** 가이드 페이지 스크롤 깊이와 내부 앵커 클릭률 비교.

### [P2][시각][관찰] 스티키 헤더가 반투명이라 스크롤 콘텐츠가 비쳐 보인다

**문제** 헤더 클래스가 `bg-white/90 backdrop-blur-md`.
**영향** 워드마크 `기준체크` 주변 가독성이 떨어진다. 심각하진 않지만 재현성이 높다.
**증거** 스크롤 중 캡처한 3개 화면에서 모두 아래 콘텐츠의 잔상 확인 — 모바일 홈 y=4,800 / 데스크톱 가이드 y=1,400 / 데스크톱 홈 y=3,400.
**수정** `bg-white/90` → `bg-white` 또는 `bg-white/95`. `backdrop-blur-md`는 유지 가능. `layout.tsx` 100행 1곳.
**검증** 같은 3개 스크롤 위치에서 재캡처 비교.

### [P2][사용성][관찰] 숫자 필드의 무음 입력 거부

**문제** 금액 필드에 `abc` 입력 → 값이 조용히 `''`로 비워지고 안내 없음(`aria-invalid=false`, `role=alert` 없음). `-500` 입력 → 부호가 조용히 제거돼 `500`이 됨.
**영향** 상한 초과는 `aria-invalid=true` + `role=alert`(`금액은 최대 999억원까지 입력할 수 있습니다.`)로 잘 처리된다. 즉 피드백 규칙이 케이스마다 달라 일관성이 깨진다(Nielsen #1 시스템 상태 가시성).
**증거** `/health-insurance/dependent/` 실측 — letters: `{val:"", invalid:"false", alerts:[]}` / overMax: `{val:"", invalid:"true", alerts:["금액은 최대 999억원까지..."]}` / negative: `{val:"500"}`.
**수정** 숫자 아닌 문자가 제거됐을 때 보조 문구 1회 노출, 음수는 상한 초과와 같은 경로로 안내. `ui.tsx` MoneyInput(173행~).
**검증** 4가지 입력(문자·음수·상한초과·정상)에 대해 각각 안내가 나오는지 e2e 추가.

### [P2][반응형][측정] 검증 원칙 페이지가 과도하게 길다

**문제** `/verification-policy/`는 모바일 22,323px(홈의 2.3배), DOM 874노드로 사이트에서 가장 무겁다.
**영향** 24px 미만 타깃 15개, 모바일 44px 미만 타깃 14개가 이 한 화면에 몰려 있다. 다만 DOM 노드는 1,500 기준 이내라 성능 문제는 아니다.
**수정** 섹션별 `<details>` 접기 또는 상시 목차. 링크 목록의 세로 패딩을 올리면 타깃 문제도 함께 해소된다.
**검증** 재수집 후 문서 높이·타깃 수 확인.

### [P2][시각][측정] 데스크톱 본문 줄 길이가 권장 범위 밖

**문제** 데스크톱 14화면 중 6화면에서 45~75자 권장 범위를 벗어난 문단이 검출됐다(가이드 1~3개 문단씩).
**재검증 결과 — 오탐** 본문 컬럼은 768px(`max-w-3xl`), 폰트 17px다. 자동 검출은 라틴 알파벳 기준(폭 ÷ 폰트크기×0.5)으로 약 90자로 계산해 임계값을 넘겼지만, 한국어는 전각 문자라 실제로는 약 **45자**로 권장 범위(35~45자) 안이다.
**수정** 조치 불필요. 자동 검사 스크립트의 줄 길이 계산에 한글(전각) 보정을 넣는 것으로 충분하다. 이 항목은 시각 점수에서 감점 요인으로 취급하지 말 것.

### [P2][사용성][가설] 판정 결론의 시각 강조가 의도적으로 약하다

**문제** 결과 헤딩(`재산요건에서 탈락할 것으로 보입니다`)이 무채색 굵은 텍스트 하나로만 처리된다.
**맥락** ADR-001·ADR-002가 "색이 결론을 곁눈질만으로 확신시킨다"는 법적 리스크를 이유로 인정/탈락 색 구분을 의도적으로 제거했다. **결함이 아니라 트레이드오프이고, 이 도메인에서 근거 있는 판단이다.**
**검토안** 색을 되돌리자는 제안이 아니다. 색 없이 주목도를 올리는 수단만 검토 — 결과 카드 상단 테두리 굵기, 결론 문장 한 단계 큰 글자, ✓/✕ 기호 확대.
**검증** 5명 사용성 테스트에서 결과 화면 도달 후 "결론이 무엇인가"를 5초 내 답할 수 있는지 측정. 이 데이터 없이 변경하지 말 것.

### [P2][사용성][가설] 데스크톱 내비게이션 항목 수

**문제** 데스크톱 14화면 중 9화면에서 가시 nav 링크가 10개를 넘는다(헤더 5 + 푸터).
**맥락** 헤더 자체는 5개(가이드·이용 방법·피부양자 판정·검증 원칙·내 자격 확인)로 Miller 7±2 안이다. 초과분은 푸터 링크가 합산된 결과라 **실질적 문제로 보기 어렵다.** 자동 검출의 한계로 기록만 남긴다.

**수집 방법**
`https://gijuncheck.kr`가 `X-Frame-Options: DENY` / `frame-ancestors 'none'`을 보내고 브라우저 창 리사이즈가 동작하지 않아, 동일 출처 `fetch` 후 `srcdoc` iframe에 주입해 뷰포트를 시뮬레이션했다(390 / 768 / 1440 / 640 / 320). CSS와 레이아웃은 실제와 동일하게 렌더된다.

**한계 — 리포트를 읽을 때 감안할 것**

1. **srcdoc iframe에서는 React 하이드레이션이 실행되지 않는다.** 따라서 42회 수집 데이터는 SSR 렌더 결과 기준이다. 레이아웃·대비·타깃 크기·구조는 영향받지 않지만, 하이드레이션 이후에만 나타나는 요소(판정 결과 섹션, 형제자매 선택 시 추가 필드 등)는 수집에 포함되지 않았다. **인터랙션 항목(모달·에러·결과·포커스)은 전부 실제 페이지에서 별도로 검증했다.**
2. **LCP를 수집하지 못했다.** bfcache 복원으로 엔트리가 기록되지 않았다. 이 항목은 점수 계산에서 제외했다.
3. **모바일 실기기 테스트는 하지 않았다.** 터치 정확도·iOS Safari 실제 동작은 시뮬레이션 결과다.
4. **스크린리더 실사용 테스트는 하지 않았다.** 자동 검사는 접근성 문제의 30~40%만 잡는다. 마크업·ARIA 구조가 우수하다는 것과 실제 스크린리더 경험이 좋다는 것은 별개다. VoiceOver / NVDA 실사용 확인을 권한다.
5. **사용자 리서치가 없다.** `가설` 태그가 붙은 항목(홈 폼 위치, 판정 결론 주목도, nav 항목 수)은 검증 방법을 함께 적었다. 검증 전에 변경하지 말 것.
