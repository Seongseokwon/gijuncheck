- 대조 사례 52건을 입력값·공단 결과·자체 결과·오차·대조일까지 표로 공개한다.
- **불일치가 났던 사례(C24·C25)를 지우지 않고 원인과 함께 남겼다.** "주택을 가지면 전월세가 재산에서 빠지고, 토지면 합산된다 — 같은 금액인데 결과가 다르다"는 발견 과정이 그대로 있다. 이런 1차 데이터는 요약 콘텐츠가 복제할 수 없고, AI가 인용할 이유가 되는 거의 유일한 지점이다.

- law.go.kr·nhis.or.kr·wetax·nts를 조항/화면 단위로 링크한다. 외부 도메인 총 12개 링크가 검증 원칙 페이지 한 곳에 몰려 있다.

이 자산은 이미 있다. 남은 일은 그것을 **정확하게 진열하는 것**이다.

## 2. P1 — 이번 스프린트

### C-1. 대조 사례 수가 세 곳에서 "13건"으로 남아 있다 (실제 30건)

**문제.** 지역보험료 대조 사례는 현재 C01~C31(C19 결번) **30건**이다. 그런데 세 곳이 여전히 13건을 말한다.

| 위치 | 현재 문구 |
|---|---|
| `src/app/page.tsx:41` | "공단 모의계산 대표 사례 **13건**을 대조했습니다" |
| `src/app/verification-policy/page.tsx:161` | "2026-08-05 공단 지역보험료 모의계산 대표 사례 **13건**을 재대조했습니다" |
| `src/lib/constants/property-score-table.ts:12,24` | "2026-08-05 … 대표 사례 **13건** 재대조 완료" (주석) |

같은 검증 원칙 페이지 안에서 위쪽 표는 13건, 아래쪽 표는 30건을 말한다. 한 화면에서 모순된다.

**영향.** 두 방향으로 손해다.
1. **신뢰.** 검증 투명성이 유일한 차별점인 사이트가 자기 검증 규모를 축소해 말하고 있다. 사용자가 두 숫자를 함께 보면 어느 쪽을 믿어야 할지 모른다.
2. **GEO.** 홈은 이 사이트에서 인바운드 링크가 가장 많은 페이지(14)다. AI가 "기준체크는 몇 건을 대조했나"를 인용한다면 13건을 가져간다. 실제 성과의 43%만 노출되는 셈이다.

**수정 방향** (코드 미반영, 제안):

```ts
// 하드코딩된 숫자를 지우고 사례 배열에서 파생시킨다.
// src/lib/verification/cases.ts 에 이미 사례 데이터가 있으므로
// 카운트를 상수로 뽑아 홈·검증원칙이 같은 값을 참조하게 한다.
export const REGIONAL_CASE_COUNT = REGIONAL_CASES.length; // 30
```
`page.tsx`와 `verification-policy/page.tsx`는 이 상수를 쓴다. 이렇게 하면 사례를 추가할 때 문구가 자동으로 따라오고, 같은 실수가 반복되지 않는다. `property-score-table.ts`의 주석은 날짜와 건수를 함께 갱신한다.

**검증.** 빌드 후 `grep -c "13건" out/**/*.html` 이 0이어야 한다. 홈과 검증 원칙 페이지에 표시된 건수가 대조 사례 표의 행 수와 같은지 눈으로 확인한다.

### C-2. `SITE.lastVerified`가 2026-08-03에 고정되어 있다

**문제.** 전역 상수 `SITE.lastVerified = '2026-08-03'`이 세 곳에 그대로 흘러간다.

- 전 페이지 푸터: "기준 · 2026년 · 최종 확인 **2026-08-03**"
- 홈 JSON-LD `WebPage.dateModified`: `2026-08-03T00:00:00+09:00`
- `privacy` / `terms` 시행일

그런데 실제 콘텐츠 최종 갱신은 **2026-08-06**이다(지역보험료·임의계속·연금 가이드·검증 원칙). 그리고 홈의 사이트맵 `lastmod`는 **2026-08-04**다.

즉 홈 한 페이지 안에서 세 개의 날짜가 서로 다르다:

| 신호 | 값 | 출처 |
|---|---|---|
| sitemap `lastmod` | 2026-08-04 | `ROUTES.home.lastModified` |
| JSON-LD `dateModified` | 2026-08-03 | `SITE.lastVerified` |
| 화면 푸터 "최종 확인" | 2026-08-03 | `SITE.lastVerified` |

**영향.** 갱신일은 GEO의 3대 신뢰 신호 중 하나이고, 매년 요율이 바뀌는 콘텐츠에서는 특히 그렇다. 세 신호가 어긋나면 어느 것도 근거로 쓰이지 않는다. 검증 원칙 페이지가 "최종 종합 검토 2026-08-06"을 말하는데 그 페이지 푸터는 08-03을 표시하는 상태다.

**수정 방향** (제안): 홈의 `dateModified`를 `SITE.lastVerified`가 아니라 `ROUTES.home.lastModified`에서 가져와 사이트맵과 같은 값을 쓰게 한다. 푸터는 "전역 최종 확인일"이라는 개념 자체가 페이지별 갱신과 충돌하므로, 페이지별 `lastModified`를 쓰거나 푸터에서 날짜를 빼는 편이 낫다.

```ts
// src/app/page.tsx — 현재
dateModified: `${SITE.lastVerified}T00:00:00+09:00`,
// 제안
dateModified: `${ROUTES.home.lastModified}T00:00:00+09:00`,
```

> **주의.** `dateModified`를 실제 수정 없이 올리는 것은 역효과다. 여기서 고칠 것은 "날짜를 최신으로 바꾸는 것"이 아니라 **세 신호가 같은 사실을 가리키게 만드는 것**이다.

**검증.** 각 페이지에서 sitemap `lastmod` = JSON-LD `dateModified` = 화면 표시 날짜, 세 값이 일치하는지 표로 확인한다. 이번 진단에서 홈만 불일치했다(나머지 10개는 일치).

### C-3. 11월 재산정 가이드의 내부 링크가 사이트에서 가장 약하다

**문제.** 인바운드 내부 링크 수:

| 페이지 | 인바운드 |
|---|---:|
| 홈 / 피부양자 판정 / 검증 원칙 | 14 |
| 지역보험료 계산 | 8 |
| 재산세 과세표준 · 임의계속 유리한 경우 | 5 |
| 임의계속가입 비교 · 자격상실 | 4 |
| 사업자등록 전 · 연금 영향 | 3 |
| **11월 일괄 재산정** | **2** |

링크하는 곳은 홈과 `losing-eligibility` 둘뿐이다. 도구 3개 페이지의 "함께 읽기"는 각각 가이드 3개만 노출하는데, 11월 가이드는 어디에도 들어가 있지 않다.

**영향.** 이 페이지는 `changeFrequency: weekly`, `priority: 0.8`로 등록된 **계절 트래픽 타깃**이다. 코드 주석도 "11월 피크를 겨냥한 글. 검색량이 몰리는 시기 전에 순위를 만들어둬야 한다"고 적고 있다. 오늘이 8월 7일이므로 색인·권위 축적에 쓸 수 있는 시간이 약 3개월 남았고, 지금이 링크를 붙일 마지막 시점에 가깝다.

**수정 방향** (제안): 도구 3개 페이지의 "함께 읽기"에 11월 가이드를 포함시킨다. 특히 `regional-premium`(11월 재산정의 결과가 곧 지역보험료다)과 `dependent`(11월에 자격상실 통보가 몰린다)에서 맥락이 자연스럽다. 앵커 텍스트는 "더보기"가 아니라 서술형으로 — 현재 사이트는 제네릭 앵커가 0건이므로 이 원칙은 이미 지켜지고 있다.

**검증.** 재빌드 후 인바운드 링크 수를 다시 세어 11월 가이드가 최소 5 이상인지 확인한다.

## 3. P2 — 백로그

### T-4. `llms.txt` 운영 응답을 확인하지 못했다

빌드 산출물 `out/llms.txt`는 4,116바이트로 정상 생성된다. 그러나 `https://gijuncheck.kr/llms.txt` 페치에서 본문이 비어 돌아왔다. 같은 방식으로 요청한 `robots.txt`는 정상 응답했으므로 도구 문제로 단정하기 어렵다.

**우선순위를 낮게 두는 이유를 분명히 한다.** Google Search는 `llms.txt`를 읽지 않는다(2026-07 갱신 공식 문서). 순위에도 AI Overviews에도 영향이 없다. 이 항목을 확인해야 하는 이유는 GEO가 아니라 **정적 자산 배포가 의도대로 되는지**를 보기 위해서다. `public/` 하위 파일이 하나라도 누락된다면 그건 다른 자산에도 해당될 수 있다.

**확인 방법.** 브라우저에서 직접 열어 본문이 보이는지, 응답 헤더의 `Content-Type`과 상태 코드가 무엇인지 본다. 정상이면 이 항목은 닫는다.

### T-5. 엔티티 URL이 canonical과 표기가 다르다

`SITE.url = 'https://gijuncheck.kr'`(트레일링 슬래시 없음)이 그대로 흘러가 Organization·WebSite·홈 WebPage의 `url`과 `@id`가 슬래시 없는 형태다. 반면 canonical과 sitemap은 `https://gijuncheck.kr/`다.

```json
"@id": "https://gijuncheck.kr#organization",   // 슬래시 없음
"url": "https://gijuncheck.kr",
// canonical: https://gijuncheck.kr/
```

`@id`는 식별자일 뿐이라 실질 위험은 낮지만, `WebPage.url`이 canonical과 다른 문자열인 것은 엔티티 해소에서 불필요한 모호함을 만든다. `next.config.mjs`가 `trailingSlash: true`인 사이트이므로 표기를 슬래시 쪽으로 통일하는 편이 일관된다.

### T-6. 도구 3개 페이지에 질문형 소제목이 없다

`dependent`·`regional-premium`·`voluntary-continuation`은 FAQPage 스키마를 갖고 있으나, 화면의 FAQ가 `<details>/<summary>`로 되어 있어 H2/H3 헤딩으로는 노출되지 않는다(질문형 헤딩 수 0). 구조화 데이터로는 인식되므로 손해가 크지는 않다. 다만 헤딩으로도 올라가 있으면 본문 텍스트만 읽는 크롤러에게도 같은 단위가 추출된다.

### T-7. OG 이미지가 페이지당 376~482KB PNG

14개 전부 PNG 원본이다(합계 약 5.6MB). 크기·비율(1200×630)과 `og:image:alt`은 정확하다. SEO 순위에는 영향이 없지만 공유 미리보기 로딩과 저장소 용량에는 영향이 있다. WebP 변환 또는 PNG 양자화로 70~80% 줄일 수 있다.

### T-8. noindex 3개 페이지의 meta description이 동일하다

`contact`·`privacy`·`terms`가 `SITE.description`을 그대로 쓴다(64자, 동일 문구). 세 페이지 모두 `noindex, follow`라 검색 결과에 나오지 않으므로 실질 영향은 없다. 기록으로만 남긴다.

### T-9. `AboutPage.dateModified` 표기가 다른 노드와 다르다

검증 원칙 페이지의 `AboutPage.dateModified`는 `"2026-08-06"`(날짜만)이고, `Article`·`WebApplication`은 `"2026-08-06T00:00:00+09:00"`(ISO+오프셋)다. schema.org는 둘 다 유효하므로 오류는 아니다. 표기 통일 항목.

### T-10. 도구 3개 페이지에 `datePublished`가 없다

`WebApplication`은 `CreativeWork` 하위라 `datePublished`를 가질 수 있는데 `dateModified`만 있다. 가이드 6개는 둘 다 있다.

### T-11. 검증 원칙 페이지 HTML이 181KB

색인 대상 중 가장 무겁다(2위 홈 102KB). 표 6개와 사례 52행이 한 페이지에 있기 때문이며, 이 밀도가 곧 이 페이지의 가치이므로 나누는 것을 권하지 않는다. 다만 CWV 실측 시 이 페이지를 우선 확인 대상으로 둘 것.

### T-12. Core Web Vitals 실측이 이번 진단에 없다

Chrome 미연결로 LCP/INP/CLS/TTFB를 측정하지 못했다. 정적 export + Vercel CDN 구성이고 페이지당 공유 JS가 103KB이므로 구조적 위험은 낮아 보이지만, **추정이지 측정이 아니다.** INP는 랩 데이터로 잡히지 않으므로 PageSpeed Insights의 CrUX 필드 데이터를 함께 봐야 한다.

**엔티티 그래프 구성이 정석이다.** `@graph` 안에서 `#organization`·`#website`·`#author` 세 노드를 `@id`로 참조해 페이지마다 중복 정의하지 않는다. `sameAs`(GitHub)와 `knowsAbout` 3개가 Organization·Person 양쪽에 붙어 있다.

**보강 여지 한 가지.** `sameAs`가 GitHub 한 개다. 엔티티 해소의 강도는 서로 다른 도메인의 앵커 개수에 비례한다. 다만 **없는 프로필을 적으면 안 된다** — 실재하고 접근 가능한 채널이 늘어날 때 추가하는 것이 맞다. 코드 주석에 이미 그 원칙이 적혀 있다.

**commodity 콘텐츠가 아니다.** 아래 구분들은 일반 요약 글에 없고, 반직관적이어서 인용 가치가 있다.

- 공시가격 ≠ 재산세 과세표준 (판정에서 가장 많이 틀리는 지점)
- 공적연금: 자격 판정에서 전액 / 보험료 계산에서 50%
- 사적연금 제외의 근거가 조문이 아니라 **공단의 자료 연계 범위**라는 설명 — 여기에 "연계 방식이 바뀌면 결론도 바뀐다"는 한계까지 붙였다
- 주택 보유 시 전월세가 재산에서 빠지지만 토지 보유 시에는 합산 (C24 vs C25)
- 농어촌 경감이 건강보험료를 깎는 것이 아니라 별도 항목으로 빠지고, 장기요양은 경감 후 금액 기준으로 계산 (C26)
