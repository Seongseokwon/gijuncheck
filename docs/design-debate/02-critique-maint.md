## 방향 A 유지보수 판정

**종합: 위험** (원안은 임계 근접, codex 수정판 반영 시 경계 초과 직전)

### 갱신 표면적
| 유형 | 개수 | 산출 근거 |
|---|---:|---|
| 코드 상수 | 21개 (leaf 값) | judge.ts가 참조하는 2026.ts 하위집합: YEAR(1)+INCOME(6)+PROPERTY(3)+SIBLING_AGE(2)+RATE(3)+BASIS(6). property-score-table.ts 130개 리터럴은 A 스코프(판정기 1개) 밖 |
| 화면 문구 | 약 71개 | 가이드 6편 하드코드 68건(grep) + 판정기 자체 프로즈("1,000만원 이하면 합산 제외" 등) 2건 + 결과 헤드라인 템플릿 1개(codex 수정판은 이 템플릿에 "2026년"을 문자열로 내장하도록 요구) |
| 가이드 문서 | 6편 | 도구가 1개뿐이라도 가이드는 손대지 않는다는 근거가 문서에 없음. 68건 하드코드 그대로 승계 |
| 기준연도 표시 지점 | 5곳 (원안 4 + codex 추가 1) | 전역 푸터(layout.tsx, 이미 존재)·홈 헤드라인("2026년 요율 7.19%")·DISCLAIMER(컴포넌트 1개)·site.ts 원본. codex 피드백이 "직접 랜딩 화면에 운영·검토 주체, 마지막 검토일, 공식 근거 링크"를 명시적으로 추가하라고 요구 — 원안이 의도적으로 숨겼던 지점을 되살림 |
| **합계** | **≈103개 갱신 지점** | |

### 연간 공수
| 작업 | 시간 |
|---|---:|
| 개정 내용 파악·확인 | 1.5h |
| 코드 상수 수정 (21개 leaf 값) | 0.5h |
| 화면 문구 수정 (판정기 1개 + 결과 템플릿) | 1.5h |
| 검증·회귀 테스트 (114개 유닛 + 단일 도구 스모크) | 1h |
| 가이드 6편 문구 갱신 (68건 스캔·수정) | 2h |
| codex 수정판 반영분: 마지막 검토일·근거링크 동기화 확인 | 1h |
| **합계** | **7.5h** |

원안(codex 수정 전)만 놓고 보면 6.5h로 8h 미만이지만, 문서가 실제로 채택 지시하는 형태(codex 피드백 반영판)는 7.5h로 임계값 바로 아래다. 여유가 30분뿐이므로 가이드 문구 스캔 시간이 조금만 늘어나거나 조항 재확인이 추가되면 바로 실패로 넘어간다.

### 갱신 누락 시나리오
- 놓쳤을 때 사용자에게 보이는 것: 원안은 "인정됩니다/탈락합니다" 단정형 헤드라인이 낡은 기준으로도 계속 확신 있게 출력된다. codex 수정판은 화면에 "2026년" 문구와 마지막 검토일을 노출하지만, 그 값 자체가 갱신되지 않으면 날짜가 붙어 있다는 사실이 오히려 "최근에 검증됐다"는 잘못된 신뢰 신호로 작동할 수 있다.
- 감지까지 걸리는 시간: 무기한. 자동 만료 경고·CI 체크가 코드에 없음(00-brief D-1). 사용자 민원이나 개발자의 우연한 재확인 전까지 발견되지 않는다.
- 그 사이 발생하는 오답의 성격: 경계선 케이스(재산 5.4억 근접, 소득 2,000만원 근접)에서 이진 결론이 반대로 뒤집혀도 확신에 찬 어조로 계속 틀린 결론을 출력한다.

### 결정적 결함
없음(연 8h 미만). 다만 codex 수정판 기준 7.5h로 임계값에 0.5h 여유밖에 없어 사실상 "1인 운영자가 조금만 바빠도 넘는" 수준이다. 결정적 결함은 아니나 구조적 위험으로 기록한다.

## 방향 B 유지보수 판정

**종합: 실패**

### 갱신 표면적
| 유형 | 개수 | 산출 근거 |
|---|---:|---|
| 코드 상수 | 163개 (leaf 값) | B는 지역보험료·임의계속가입 카드를 "검증 중" 배지로 화면에 유지하므로(3절), 이 두 도구가 참조하는 property-score-table.ts 130개 리터럴 + 2026.ts 30개 leaf값 + BASIC_DEDUCTION·VERIFIED류 2개 = 163개가 전부 "화면에 걸려 있는" 상태로 유지보수 대상이다. 비공개라도 코드·UI에 존재하는 한 리스크는 사라지지 않는다 |
| 화면 문구 | 약 82개 | 가이드 6편 68건(공유) + 판정기 자체 2건(공유) + 결과 템플릿(3단계 체크리스트 문구, 충족/미충족/조건부 3종) + 홈 허브 도메인 3개 섹션 헤더·상황 기반 진입 라우터 3~4개 + 카드별 빌드상태 배지 문구 3종 |
| 가이드 문서 | 6편 + "읽을거리" 목록 분리 관리 | 동일 68건 승계, 여기에 "판단 도구와 배경지식을 다른 인지 부하로 분리"한 홈 배치 로직 유지 추가 |
| 기준연도 표시 지점 | 14곳 (추정) | 공유 기본 8곳(전역 푸터·홈 헤드라인·DISCLAIMER 컴포넌트 3개·가이드 템플릿·regional-premium 페이지 타이틀·site.ts) + 빌드상태 배지 3종(이용가능/검증중/준비중 — 각 배지가 "이 상태가 여전히 맞는지" 매년 재확인 대상) + 결과유형별 교차링크 추천 로직 3곳(B 문서 7절이 스스로 명시) |
| **합계** | **≈265개 갱신 지점** | |

### 연간 공수
| 작업 | 시간 |
|---|---:|
| 개정 내용 파악·확인 (도구 간 파급 포함) | 2h |
| 코드 상수 수정 (2026.ts + 상태 플래그 동기화) | 1h |
| 화면 문구 수정 (활성 도구 1개 + 홈 허브 카드·배지·라우터 + 교차링크 3곳) | 3h |
| 검증·회귀 테스트 (내비게이션·배지·크로스링크 조합까지 포함한 회귀) | 2.5h |
| 가이드 6편 문구 갱신 | 2h |
| **합계** | **10.5h** |

B 문서 7절 스스로 "도구 개수 × 상태(3단계) × 결과 유형(3종) 조합 수만큼 문구·배지·교차링크 정합성을 점검해야 하며, 도구가 늘어날수록 점검 조합 수가 곱으로 증가한다"고 밝히고 있다. 이는 곧 "법령 수치는 안 바뀌어도 상태 조합 점검만으로 매년 일정 시간을 쓴다"는 뜻이며, 실제 개정 여부와 무관한 고정 오버헤드가 매년 발생한다는 자기 진술이다.

codex 피드백은 "축소형 B"(단일 활성 도구)를 권고하지만, 그 축소판도 국민연금·고용보험용 "준비 중" 카드와 3색 도메인 팔레트, 지역보험료·임의계속가입의 "검증 중" 배지 인프라를 코드에 남겨둔 채로 "상태 플래그 하나로 동시에 열리도록" 설계하라고 지시한다. 즉 화면 노출은 줄어도 유지해야 할 상태 동기화 로직 자체는 사라지지 않는다. 축소판을 적용해도 위 표의 코드 상수 163개, 배지 3종 관리 의무는 잠재 형태로 남아 실질 공수를 8h 아래로 내리지 못한다(축소판 추정 약 8~9h, 여전히 경계 초과).

### 갱신 누락 시나리오
- 놓쳤을 때 사용자에게 보이는 것: 특정 도구만 갱신되고 다른 도구는 갱신되지 않는 부분 오염(partial staleness)이 발생해도, 홈 화면의 빌드상태 배지("이용 가능")는 값의 최신성이 아니라 도구의 가동 여부만 표시하므로 사용자는 여전히 "정상 서비스 중"으로 인지한다.
- 감지까지 걸리는 시간: 무기한. 배지 시스템 자체가 "최신성"이 아니라 "가동성"을 표시하도록 설계되어 있어, 값이 낡아도 배지는 바뀌지 않는다 — 감지 메커니즘이 구조적으로 부재한다.
- 그 사이 발생하는 오답의 성격: 여러 도구에 걸친 교차 추천("이것도 확인해보세요")이 낡은 값을 근거로 사용자를 다른 낡은 계산 결과로 계속 유도하는, 단일 도구보다 전파 범위가 넓은 오답이 발생한다.

### 결정적 결함
연 8h 초과(10.5h, 축소판 적용해도 8~9h로 경계 초과). B 스스로 인정한 "조합 수의 곱셈적 증가"가 1인 운영 전제와 정면으로 충돌한다.

C 문서 7절이 스스로 "기존 대비 1.5~2배" 공수를 인정하며, 그 근거로 "조항 번호·시행일 표기의 정확성까지 매년 재검증해야 한다"고 명시한다. 이는 일반 상수 갱신(값이 맞는지)과 별개로, 매년 개정이 없더라도 "조항이 재배열·재번호됐는지" 확인하는 독립 작업이 추가된다는 뜻이며, 이 작업은 코드 diff로 자동 검증할 수 없고 사람이 법제처 원문을 열어 대조해야 한다.

### 갱신 누락 시나리오
- 놓쳤을 때 사용자에게 보이는 것: "대조 완료/미검증" 배지와 lastChecked 날짜가 그대로 화면에 남는다. C는 A·B와 달리 이 상태를 상시 노출하도록 설계되어 있으므로(4절 "펼쳐야 보이는 정보로 두지 않는다"), 갱신을 놓쳤다는 사실이 오히려 가장 잘 드러나는 구조다.
- 감지까지 걸리는 시간: 이론적으로는 가장 짧다(날짜가 상시 노출되므로 사용자가 스스로 계산 가능). 그러나 "마지막 확인일을 표시하는 안은 갱신 주기가 연 1회가 아니라 상시가 된다" — 날짜가 오래될수록 신뢰가 능동적으로 무너지고, 운영자는 값이 안 바뀌었어도 lastChecked만 매번 다시 찍기 위해 재검토를 반복해야 하는 압박을 받는다. 이는 감지가 빠른 대신 유지보수 부담이 "연 1회"가 아니라 "상시"로 바뀌는 구조적 함정이다.
- 그 사이 발생하는 오답의 성격: 조항 번호·시행일 오기재는 값 자체는 맞아도 "추적 가능성"이라는 이 안의 핵심 약속을 깨뜨린다. 즉 정답을 주면서도 근거를 못 믿게 만드는, C 특유의 역효과(9절에서 C 스스로 이 실패 조건을 명시)가 발생한다.

### 결정적 결함
연 8h 초과(10.5h) + 누락 시 화면에 노출되는 lastChecked/검증 배지가 오히려 "상시 갱신 의무"를 만들어내는 구조. 값 자체보다 메타데이터(조항 번호·시행일) 정확성 검증이 자동화 불가능한 수작업이라는 점이 B보다 더 근본적인 결함이다 — B는 조합 수가 문제고, C는 검증 방법 자체가 사람 손을 벗어날 수 없다는 게 문제다.
