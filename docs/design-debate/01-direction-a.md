# 방향 A: 검색 유입 사용자를 위한 단일 판정 도구 — 결론 우선, 단정형

## 0. 이 안의 목적함수
검색으로 들어온 사용자가 클릭과 스크롤을 최소로 거쳐 "인정됩니다 / 탈락합니다"라는 단정적 결론에 도달하기까지의 시간을 최대한 짧게 만드는 것을 최대화한다.

## 1. 거부한 전제
| Brief의 전제 # | 거부 이유 |
|---|---|
| 5 | "40~60대가 주 사용자다"라는 가정을 받아들이면 글자를 키우고 여백을 넓혀야 하는데, 그러면 11필드 단일 화면이 스크롤을 유발해 "가장 빠르게 결론에 도달"이라는 목적함수와 직접 충돌한다. 이 방향은 특정 연령층이 아니라 "지금 급하게 답을 찾는 검색 사용자" 일반을 대상으로 삼고, 연령 가정 대신 "결과까지 스크롤 1회 이내"를 제약으로 채택한다. |

## 2. 유입과 랜딩 가정
- 사용자가 이 서비스에 도달하는 경로: "피부양자 자격 조건", "건강보험 피부양자 재산 기준" 등 구체적 판정 관련 검색어로 검색엔진 결과 페이지에서 클릭 (D-2가 지적한 "색인 단일 경로 의존"을 그대로 받아들이고 그 경로 안에서만 최적화한다)
- 첫 화면으로 가정하는 페이지: `/health-insurance/dependent/` 자체. 홈(`/`)이 아니라 판정 도구 페이지가 사실상의 랜딩이다.
- 이 가정이 틀리면 무너지는 부분: 실제로는 가이드 페이지(예: "피부양자 재산 기준 완전정리")로 먼저 들어와 배경지식을 얻은 뒤 도구로 넘어오는 2단계 여정이 다수라면, 홈·가이드를 얇게 만들고 도구 하나에 자원을 몰아준 이 설계가 오히려 이탈을 늘릴 수 있다. 브랜드 검색("사대보험")으로 들어와 서비스 전체 범위를 먼저 살피는 사용자에게는 이 랜딩이 "이게 전부인가"라는 인상을 줄 수 있다.

## 3. 홈 구조
가정한 랜딩이 홈이 아니므로 그 이유를 밝힌다. 홈(`/`)은 사실상 판정 도구로 가는 통로 역할만 한다. 헤드라인 한 줄("피부양자 자격, 지금 확인하세요"류), CTA 버튼 하나, 그 아래 이 도구가 무엇을 판정하는지 1문장 — 이것이 홈의 전부다. 가이드 6편 목록, 다른 도구 소개, 팁·뉴스 등 부가 정보는 홈에 노출하지 않는다. 홈은 정보 페이지가 아니라 도구로 가는 스플래시다. (지역보험료 계산기·임의계속가입 비교는 Brief의 선결 결정에 따라 이미 비공개이므로 홈 내비게이션에 애초에 등장하지 않는다 — 이 방향은 그 결정과 자연히 부합한다)

## 4. 입력 화면 구조
- 화면 분할 방식: 단일 화면, 단일 카드. 위저드·스텝 분리를 하지 않는다(스텝 분리는 클릭 수를 늘려 목적함수와 정면으로 충돌한다). 입력 완료 즉시 결과가 보이도록 제출 버튼을 화면 하단에 고정한다.
- 입력 항목 수: 기존 구조상 필드 수(최대 11개, 조건부 노출 포함)는 유지한다 — 코드 변경 없이 시각적으로만 조정한다. 다만 대다수 사용자가 "아니오/0"으로 응답할 가능성이 높은 항목(금융소득, 기타소득, 사업자등록 여부)은 기본값으로 접어두고 "해당사항 있음" 토글로만 펼친다. 화면에 처음부터 보이는 필드 수를 6~7개 수준으로 낮춰 체감 밀도를 줄인다.
- 각 항목의 설명 노출 방식: 근거·기준 설명(hint)은 기본적으로 숨기고 "?" 아이콘 탭 시에만 팝오버로 노출한다. 라벨 자체는 최소 단어로 압축해, 설명을 읽지 않고도 입력이 가능한 사람은 그대로 통과하도록 한다.

## 5. 결과 화면 구조
- 정보 제시 순서: 결론(인정/탈락)을 화면 최상단, 가장 큰 시각 요소로 배치한다. 그 아래 한 줄 요약 이유. 근거 조항·계산 과정은 기본 접힘 상태이며 "자세히 보기" 클릭 시에만 펼쳐진다.
- 결론 표현의 강도와 정확한 문구 예시: 단정형으로 통일한다. "인정됩니다." / "탈락합니다." 헤징 표현("~로 보입니다")은 쓰지 않는다. Brief가 지적한 헤드라인의 헤징·단정 혼재는 이 방향에서 전면 단정 쪽으로 정리해야 함을 명시한다.
- 다음 행동 제시 방식: 다른 도구(지역보험료 계산 등)로의 유도는 하지 않는다 — mandate A의 범위 밖이며, 해당 도구들이 현재 비공개이기도 해 자연히 부합한다. 결과 화면 하단에는 "다시 확인" 버튼과 관련 가이드 1편으로의 텍스트 링크만 둔다. 카드형 추천, 다중 링크는 배제한다.

## 6. 시각 체계
- 색상
  - 전역 배경: `#FFFFFF` (단일 톤)
  - 기본 텍스트: `#0A0A0A`
  - 보조/힌트 텍스트(펼쳤을 때만 노출): `#6B7280`
  - 인정 결과: 배경 `#15803D`, 텍스트 `#FFFFFF`
  - 탈락 결과: 배경 `#B91C1C`, 텍스트 `#FFFFFF`
  - 버튼(기본): 배경 `#0A0A0A`, 텍스트 `#FFFFFF`, hover `#262626`
  - 입력 테두리: `#D1D5DB`
- 타이포 스케일
  - 결과 헤드라인: 40px / bold(700) / line-height 1.15
  - 카드 제목: 18px / semibold(600)
  - 입력 라벨: 15px / medium(500)
  - 버튼: 18px / bold(700)
  - 접힌 설명·힌트(펼쳤을 때만): 13px / regular(400)
  - 푸터/면책: 12px
- 간격 스케일: 4 / 8 / 12 / 16 / 24 / 32px (6단계, 촘촘하게). 콘텐츠 최대폭: 560px (데스크톱 포함, 모바일은 100% width - padding 16px)

### 유도 근거
| 결정 | 값 | mandate에서 유도됨 / 관습 | 유도 과정 |
|---|---|---|---|
| 배경 단일톤 | `#FFFFFF` 전역 | 유도 | 배경-카드 2단 배색은 사용자가 "구역"을 눈으로 구분해야 하는 인지 비용을 추가한다. 단일 톤으로 그 구분 자체를 없애 스캔 경로를 단순화한다 |
| 기본 텍스트 | `#0A0A0A` | 유도 | 대비 여유를 최대화해두면 보조 텍스트조차 진한 값을 쓸 수 있어, 결과적으로 화면 전체의 스캔 속도 상한이 넓어진다 |
| 인정 결과 배경 | `#15803D` 솔리드 | 유도 | 파스텔 틴트(연한 배경+진한 텍스트)는 읽어야 인지되지만, 고채도 솔리드 블록은 곁눈질만으로도 "좋은 결과"임이 인지된다 — 결론을 읽지 않고 보게 하는 것이 목적함수다 |
| 탈락 결과 배경 | `#B91C1C` 솔리드 | 유도 | 위와 동일한 논리. 두 색을 서로 다른 채도·톤의 솔리드로 명확히 대비시켜 즉시 판별 가능하게 한다 |
| 버튼색 | 텍스트와 동일한 무채색 `#0A0A0A` | 유도 | 새 강조색을 추가하면 사용자가 "색이 뭘 의미하는지" 하나 더 학습해야 한다. 결과 화면의 색 의미를 인정/탈락 2개로 제한하기 위해 버튼은 신규 색 없이 최고대비 무채색을 쓴다 |
| 보조/힌트 텍스트 색 | `#6B7280` | 관습 | 이 텍스트는 사용자가 스스로 "자세히 보기"를 펼쳤을 때만 존재한다. 기본 화면 스캔 경로에 들어오지 않으므로 mandate가 이 값을 특정하지 않는다. 관습적 중간 회색을 그대로 채택 |
| 폰트 | 커스텀 웹폰트 미사용, 시스템 산세리프 | 유도 | 웹폰트 로딩 지연은 첫 화면 페인트를 늦추고, 이는 "결론 도달 시간"이라는 목적함수 지표를 직접 침해한다. 0ms 로딩을 위해 시스템 폰트를 고정한다 |
| 결과 헤드라인 크기 | 40px bold | 유도 | 결론을 "읽지 않고 보이게" 만들려면 화면에서 가장 큰 단일 시각 요소여야 한다 |
| 입력 라벨 크기 | 15px | 관습 | 입력 필드 자체의 크기는 가독 최소선만 넘으면 되고 mandate가 특정 값을 요구하지 않는다. 관습적 값 채택 |
| 접힌 설명 크기 | 13px | 관습 | 위와 같은 이유로 기본 노출되지 않는 콘텐츠의 크기는 목적함수와 무관하다 |
| 버튼 크기 | 18px bold, 높이 48px | 유도 | 화면에서 가장 먼저 눌러야 할 단일 행동을 지연 없이 찾게 하려면 시각적으로 압도적인 크기와 대비가 필요하다 |
| 콘텐츠 최대폭 | 560px (데스크톱 포함) | 유도 | 폭을 좁혀 가로 스캔(눈동자 좌우 이동)을 없애고 세로 한 줄 경로만 남긴다. 넓은 폭은 데스크톱에서 "더 볼 게 있나" 하는 좌우 탐색을 유발해 목적함수를 방해한다 |
| 간격 스케일 | 4/8/12/16/24/32px, 기존보다 촘촘 | 유도 | 스크롤 거리는 목적함수의 직접 지표(첫 결과까지의 스크롤 횟수)다. 여백을 압축해 스크롤 자체를 줄인다 |
| Radius | 4px | 관습 | 모서리 둥글기가 스캔 속도에 영향을 준다는 근거를 mandate에서 찾을 수 없다. 임의의 최소값을 채택했음을 명시한다 |

## 7. 갱신 부담
- 기준이 바뀌면 수정해야 하는 지점: `constants/2026.ts` 1개 파일, 판정 도구 결과 화면의 단정형 카피(수치를 직접 언급하는 문장이 있다면 그 부분), 가이드 6편 문구 내 숫자 34건, 접힌 설명(펼쳤을 때 보이는 근거 조항 텍스트).
- 연 1회 갱신 시 예상 작업량: 이 방향은 지역보험료·임의계속가입·국민연금·고용보험을 애초에 다루지 않으므로, 3~4개 도구가 아니라 판정기 1개 + 가이드 6편만 검토 대상이다. 다른 두 도구가 언젠가 재공개되더라도 이 방향의 결과 화면·설계는 그 시점까지 갱신 대상에서 완전히 제외된다 — 구조적으로 갱신 범위가 가장 좁다.

## 8. 포기한 것
| 포기한 가치 | 왜 포기해도 되는가 |
|---|---|
| 확장성 | 지역보험료·임의계속가입·국민연금·고용보험을 위한 정보구조(내비게이션, 공통 컴포넌트 패턴)를 지금 설계하지 않는다. 그 도구들이 나중에 재공개·신규 개발될 때 이 화면의 언어(솔리드 컬러 결과 블록, 좁은 폭, 접힌 설명)를 그대로 재사용하지 못하고 별도로 다시 설계해야 할 수 있다 |
| 판단 근거에 대한 신뢰 구축 | 근거 조항·계산식을 기본 숨김 처리하면, "왜 이런 결과가 나왔는지" 검증하려는 사용자(실무자, 꼼꼼한 당사자)는 즉시 이탈하거나 결과를 신뢰하지 않을 수 있다. 이 방향은 그 사용자층을 의도적으로 포기한다 |
| 오판정에 대한 완충 | 결과를 "인정됩니다/탈락합니다"로 단정하면, 실제 공단 심사와 다를 경우(모의계산이라는 성격상 항상 존재하는 오차) 사용자가 "틀렸다"고 느낄 여지가 헤징 문구보다 크다. 면책 문구가 있어도 헤드라인의 단정적 어조가 그 효과를 상당 부분 상쇄한다 |
| 탐색·비교 경험 | 사용자가 자기 상황을 다각도로 비교(소득 시나리오별 결과 비교 등)하는 기능을 배제한다. 경계선 케이스(예: 재산이 5.4억에 근접)에서 "얼마나 여유가 있는지" 같은 부가 정보 없이 이진 결과만 제공한다 |
| 홈 화면의 서비스 전체상 전달력 | 홈이 도구로 가는 통로로 축소되므로, 브랜드 검색으로 들어온 사용자에게 "이 서비스가 전체적으로 뭘 하는 곳인지" 보여주지 못한다 |

## 9. 이 안이 실패하는 조건
- 실제 트래픽 데이터에서 사용자가 도구 페이지가 아니라 가이드 페이지로 먼저 대량 유입되고, 거기서 도구로의 전환율이 낮다는 사실이 확인되면(2절의 랜딩 가정이 틀리면) 홈·가이드를 최소화한 이 구조는 폐기해야 한다.
- "인정됩니다/탈락합니다" 같은 단정형 결과 문구 때문에 실제 공단 판정과 달랐다는 민원·항의 사례가 확인되면, 축2(단정)를 헤징으로 되돌려야 하며 이 안의 핵심 전제가 무너진다.
- 향후 사업 방향이 "여러 사회보험 도구를 통합 서비스로 확장"하는 쪽으로 확정되면(로드맵상 국민연금·고용보험 착수), 이 안이 8절에서 포기한 확장성 부채가 그대로 현실화되어 정보구조를 전면 재작업해야 한다.

- 비공개 계산 도구로 유도하지 않는 정책

### 폐기·수정할 요소

- `"인정됩니다/탈락합니다"`는 `"현재 입력과 2026년 기준으로는 요건을 충족하는 것으로 계산됩니다"`처럼 조건부로 바꾼다.
- 근거·기준연도·최종 판정 주체를 팝오버나 12px 푸터에만 숨기지 않는다.
- 고채도 성공·실패 블록이 면책보다 강하게 읽히지 않도록 상태색은 보조 신호로 사용한다.
- 직접 랜딩 화면에 민간 정보 서비스 표기, 운영·검토 주체, 마지막 검토일, 공식 근거 링크를 배치한다.

이 안의 목적함수인 `가장 빠른 단정적 결론`은 더 이상 최상위 목표가 아니다. 수정된 목표는 `빠르게 이해할 수 있으면서 검증 가능한 조건부 결론`이다.
