기준체크 UI 감사 리포트

https://gijuncheck.kr · 감사일 2026-08-05 · 데스크톱 Chrome 실제 렌더링 + DOM/CSS/성능 계측

총평. 완성도가 상당히 높은 사이트입니다. 시맨틱 구조, 구조화 데이터, 성능, 면책 고지, 근거 조항 노출은 이 카테고리 평균을 크게 웃돕니다. 특히 0원 입력 확인 모달과 단계별 판정 근거 + 법령 원문 링크는 제품의 차별점이 UI로 제대로 구현된 사례입니다.

다만 금액 입력 필드의 단위 문제 하나가 나머지 장점을 무력화할 수 있는 수준입니다. 입력 단위는 원인데 화면 어디에도 "원"이라고 쓰여 있지 않고, 사이트의 모든 카피·FAQ·결과 요약은 만원/억원을 씁니다. 판정 결과가 정반대로 뒤집힐 수 있는 경로이므로 최우선 처리 대상입니다.

1. Critical

CRITICAL금액 입력 단위가 화면에 표시되지 않음

피부양자 판정 · 지역가입자 보험료 · 임의계속가입 — 전 계산기 공통 · 소득/재산 입력 필드 전체

모든 금액 필드의 실제 입력 단위는 원입니다. 그런데 라벨은 사업소득, 플레이스홀더는 0일 뿐이고, 필드 안이나 옆에 단위 표기가 없습니다. 반면 같은 화면의 요약은 현재 합산소득 0만원, FAQ는 연 2,000만원, 결과는 재산세 과세표준 0억원으로 전부 만원·억원 단위입니다.

실제로 확인한 동작입니다.

사용자가 입력한 값시스템이 해석한 금액판정 결과
3000 (3,000만원이라 생각)3,000원 = 0.3만원"자격이 인정될 것으로 보입니다"
300000003,000만원"소득요건에서 탈락할 것으로 보입니다" (정상)

즉 탈락해야 할 사람에게 "인정" 결과가 나옵니다. 재산 필드는 더 위험합니다. 6억을 뜻하며 6을 치면 6원으로 계산되어 재산요건을 무조건 통과합니다.

현재 유일한 단서는 입력 후에 필드 아래 작은 회색 글씨로 나타나는 3,000원 에코 하나뿐입니다. 우측 정렬된 숫자 아래 13px 보조 텍스트라 놓치기 쉽고, 스크린리더에는 aria-describedby로 연결조차 되어 있지 않습니다.

권장 조치
  • 필드 안에 고정 접미사 원을 항상 표시 (입력 전에도 보이도록)
  • 라벨을 사업소득 (원)으로 변경, 플레이스홀더를 예: 30,000,000으로
  • 이미 잘 하고 있는 패턴이 사내에 있습니다 — 임의계속가입 페이지의 퇴직 전 12개월 보수월액 평균은 3,000,000을 프리필해서 300만원 에코를 처음부터 보여줍니다. 이 방식을 전 필드로 확대하는 것만으로도 상당 부분 해소됩니다.
  • 보조안: 만원 단위 입력 토글 제공

2. High

HIGH판정 후 결과로 포커스·스크롤이 이동하지 않음

전 계산기 공통 · 결과 렌더링 직후

버튼 클릭 후 결과는 버튼에서 약 150px 아래에 렌더링됩니다. 그런데 document.activeElement는 BODY로 남고 스크롤도 0px 움직이지 않습니다(계측값). 긴 폼을 다 채우고 화면 하단에서 버튼을 누른 사용자에게는 아무 일도 일어나지 않은 것처럼 보일 수 있습니다.

흥미롭게도 0원 확인 모달에서는 포커스 이동이 정상 구현되어 있습니다(입력 수정하기 버튼으로 진입). 결과 영역에만 빠져 있습니다.

권장 조치 
<h3 tabIndex={-1} ref={resultRef}>소득요건에서 탈락할 것으로 보입니다</h3>

// 판정 완료 후
resultRef.current?.focus();
resultRef.current?.scrollIntoView({ block: 'start', behavior: 'smooth' });
포커스를 결과 헤딩으로 옮기면 시각 사용자에게는 스크롤이, 스크린리더 사용자에게는 낭독이 동시에 해결됩니다.

HIGH입력 상한이 없어 결과 문자열이 깨짐

피부양자 판정 · 소득/재산 필드

999999999999999를 입력해도 그대로 수용되며, 결과 요약이 다음과 같이 출력됩니다.

확인에 사용한 입력 · 합산소득 100,000,003,000.01만원 · 재산세 과세표준 6억원

자릿수 문제 외에 .01이라는 부동소수점 오차가 그대로 노출됩니다. "근거까지 보여준다"를 내세운 서비스에서 신뢰를 직접 깎는 표시입니다.

권장 조치 필드별 현실적 상한 설정(예: 소득 999억, 재산 9,999억)과 초과 시 안내 메시지. 만원 환산 시 Math.round() 적용해 소수점 제거. 참고로 임의계속가입의 개월수 필드는 이미 18로 클램프되고 있으므로 동일 유틸을 재사용할 수 있습니다.

3. Medium

MEDIUM입력 필드에 aria-describedby가 연결되어 있지 않음

전 계산기 · 11개 필드 전수 확인 — aria-describedby 모두 null

필드 아래 보조 설명이 스크린리더에 전달되지 않습니다. 누락되는 정보가 하필 이 서비스의 핵심입니다.

  • "실거래가·공시가격이 아니라 지방세 재산세 과세표준을 입력합니다" — 사이트가 가장 많이 틀리는 지점이라고 직접 명시한 내용
  • "이자·배당 합계가 연 1,000만원 이하면 소득 합산에서 제외됩니다"
  • 단위 에코 3,000원 (Critical 항목과 직결)

라벨 자체는 aria-labelledby로 잘 연결되어 있으므로, 같은 방식으로 설명 텍스트에 id를 부여해 연결하면 됩니다.

권장 조치 <input aria-labelledby="lbl-x" aria-describedby="hint-x unit-x">

MEDIUM모달을 닫은 뒤 포커스가 트리거로 복원되지 않음

0원 확인 모달 · Esc 및 확인 후 공통

모달 자체는 훌륭합니다 — role="dialog", aria-modal="true", aria-labelledby, 진입 시 포커스 이동, Esc로 닫힘까지 모두 구현되어 있습니다. 다만 닫은 뒤 document.activeElement가 BODY로 돌아갑니다. 키보드 사용자는 폼 맨 위부터 다시 Tab해야 합니다. (WCAG 2.4.3 Focus Order)

권장 조치 모달 언마운트 시 내 자격 판정하기 버튼으로 .focus() 복원.

MEDIUM명도 대비 WCAG AA 미달 2건

권장 조치 둘 다 아슬아슬한 차이라 색을 한 단계만 어둡게 하면 해결됩니다. #64748B → #566575(5.59), #087E8B → #056D78(5.34)이면 여유 있게 통과합니다. 주 사용자층이 퇴직 전후 연령대라 대비 여유를 두는 편이 특히 유리합니다.

MEDIUMSkip link 없음

전 페이지 · <body> 첫 링크가 로고

키보드·스크린리더 사용자가 페이지를 열 때마다 헤더 내비게이션 5개 링크를 통과해야 본문에 도달합니다. (WCAG 2.4.1 Bypass Blocks)

권장 조치 <body> 최상단에 <a href="#main" class="sr-only focus:not-sr-only">본문 바로가기</a> 추가. <main>은 이미 1개만 존재하므로 id만 부여하면 됩니다.

MEDIUM판정 결과 전체가 aria-live="polite" 영역

전 계산기 · 계측된 결과 텍스트 약 900자

결과 컨테이너 전체가 live region이라 3단계 판정·근거 조항·다음 확인 사항이 한 번에 통째로 낭독됩니다. 중간에 건너뛰거나 되돌아가기 어렵습니다.

권장 조치 live region은 "소득요건에서 탈락 — 자세한 내용은 아래" 수준의 짧은 요약만 담고, 본문은 위 High 항목의 포커스 이동으로 처리.

4. Low

LOW세부 개선 항목

항목내용 및 권장
푸터 링크 터치 타깃검증 원칙·개인정보처리방침·이용약관·문의 모두 높이 23px. 권장 44px. 헤더 로고·툴팁은 이미 44px을 지키고 있어 푸터만 예외입니다.
가이드 표 접근성가이드 문서의 표에 <caption>과 th[scope]가 없습니다. 재산 구간표처럼 판정에 직결되는 표라 스크린리더 탐색성을 높일 가치가 있습니다.
Breadcrumb 시각 노출BreadcrumbList JSON-LD는 있으나 화면에는 breadcrumb이 없습니다. 가이드 → 판정기 간 이동이 잦은 구조라 상단 경로 표시가 유용합니다.
개월수 필드 서식임의계속가입의 퇴직 전 18개월 중 직장가입 개월수가 금액 필드와 동일한 우측정렬·콤마 서식이라 단위 혼동을 유발합니다. 또한 999 입력 시 조용히 18로 클램프되며 안내가 없습니다.
포커스 링 트리거:focus-visible 대신 :focus를 사용해 마우스 클릭에도 링이 표시됩니다. 접근성상 문제는 아니나 시각적 노이즈입니다.
새 창 링크 안내법령·위택스 등 외부 링크가 target="_blank"인데 새 창이 열린다는 표시가 없습니다. (WCAG 3.2.5) rel은 정상입니다.
결과 저장 수단인쇄·이미지 저장·링크 공유가 없습니다. 공단 상담(1577-1000)에 결과를 들고 가는 것이 자연스러운 흐름이므로 인쇄용 스타일시트만 추가해도 효용이 큽니다.

5. 잘 되어 있는 점

GOOD계측으로 확인된 강점

영역확인 내용
0원 확인 모달빈 폼 제출 시 0원 입력 항목을 확인해 주세요 모달이 항목을 나열하며 되묻습니다. role="dialog" + aria-modal + aria-labelledby + 포커스 진입 + Esc 닫힘까지 정석대로 구현되어 있습니다. 이 감사에서 가장 인상적인 부분입니다.
결과 설계부양·소득·재산 3단계를 각각 통과/탈락 + 사유 + 다음 확인 사항 + 법령 원문 링크로 제시합니다. "결과보다 근거까지"라는 약속이 실제 UI로 구현되어 있습니다.
툴팁<button> + aria-label="도움말: …" + aria-describedby + aria-expanded + 44×44px 타깃. 교과서적입니다.
모바일 기본기입력 필드 폰트 전부 16px(iOS 자동 확대 방지), inputmode="numeric", viewport 메타 정상, user-scalable 제한 없음, 고정 min-width 0건, 모바일 우선 Tailwind(sm: 42회).
성능CLS 0, TTFB ~14ms, HTML 11KB(gzip)/55KB, 리소스 14개, 웹폰트 0개(시스템 폰트 스택 → FOIT/FOUT 없음). 계산기 페이지 DOM 258노드로 매우 가볍습니다.
구조화 데이터Organization, WebSite, WebPage, Article, BreadcrumbList, FAQPage, ItemList 완비.
SEO 기본canonical, OG/Twitter 카드 전 페이지, 페이지별 og:image, robots.txt + sitemap.xml(lastmod 포함), 404가 실제 404 상태 반환.
시맨틱·랜드마크페이지당 h1 1개, 헤딩 레벨 건너뛰기 없음, <main> 1개, nav에 aria-label("데스크톱 주요 메뉴"/"모바일 주요 메뉴"), aside에도 라벨 부여.
포커스 관리 기반양수 tabindex 0건, outline:none 남용 0건, 대체 링(focus:ring-4) 적용.
모션prefers-reduced-motion 대응 규칙 존재.
입력 정제abc-99 → 99로 자동 정제. 개월수는 18로 자동 클램프.
상태 표시통과/탈락이 색뿐 아니라 ✓/✕ 글리프로 구분되고, sr-only 텍스트로도 제공됩니다.
면책 고지상단 배너 + 결과 내부 + 푸터 3중 노출. 기준연도와 최종 확인일까지 명시.
외부 링크전부 rel="noopener noreferrer".

6. 처리 순서 제안

순위작업예상 난이도
1금액 필드에 원 단위 상시 표시 (라벨·플레이스홀더·접미사)낮음 · 영향 매우 큼
2판정 결과 헤딩으로 포커스 + 스크롤 이동낮음
3입력 상한 설정 및 만원 환산 반올림낮음
4보조 설명·단위 에코에 aria-describedby 연결낮음
5모달 닫힘 시 포커스 복원낮음
6대비 미달 2색 조정매우 낮음
7Skip link 추가, 푸터 터치 타깃 확대매우 낮음
8결과 인쇄 스타일, 시각 breadcrumb, 표 scope/caption중간
감사 범위와 한계
  • 확인한 페이지 — 홈, 피부양자 자격판정, 지역가입자 보험료 계산, 임의계속가입 비교, 가이드(재산세 과세표준), robots.txt, sitemap.xml, 404
  • 방법 — 실제 Chrome 렌더링 스크린샷, DOM/ARIA 전수 조사, 전체 텍스트 노드 명도 대비 계산, 폼 입력·제출·모달·결과 흐름 직접 실행, Navigation/Resource/LayoutShift Timing 계측
  • 검증하지 못한 것 — 브라우저 창 리사이즈가 탭 뷰포트에 반영되지 않아 실제 모바일 폭(360~430px) 렌더링은 육안 확인하지 못했습니다. 위 모바일 항목은 CSS·마크업 구조 분석에 근거한 것이므로, 실기기 또는 DevTools 디바이스 모드로 한 번 확인하시길 권합니다.
  • 범위 밖 — 판정 로직의 법령 정확성, 보안, 크로스 브라우저(Safari/Firefox), 실사용자 테스트
